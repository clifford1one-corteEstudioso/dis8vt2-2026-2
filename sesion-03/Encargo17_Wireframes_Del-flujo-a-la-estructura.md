# **Encargo 17: Wireframes: Del flujo a la estructura**

# **Definición & propósito**

Un **wireframe** es un plano (de baja, media o alta fidelidad gráfica según se requiera)  que muestra cómo está organizada la información y cómo navega el usuario a través de una interfaz digital. En su nivel de baja y media fidelidad no es un diseño visual —no incluye colores, tipografía, ni ilustraciones— sino una estructura esquemática que responde: ¿dónde va cada elemento? ¿qué controles necesita el usuario? ¿cómo se conectan las acciones entre pantallas?

Piénsalo como el plano arquitectónico de tu producto digital. El flujo de usuario (LEnguaje Visual que vimos de J.J. Garrett) muestra **qué ocurre** en la experiencia; el wireframe muestra **cómo lo ve el usuario en pantalla** u otra interfaz.

# **Relación con diagramas de flujo**

Los diagramas de flujo (Garrett) y los wireframes funcionan en tándem:

| Diagrama de flujo (Garrett) | → | Wireframe |
| ----- | ----- | ----- |
| Define **etapas, decisiones, actores** |  | Especifica **componentes de interfaz** |
| "El usuario entra, ve opciones, elige una" |  | "La pantalla tiene un menú, botones aquí, contenido ahí" |
| Horizontal (carril de usuario, sistema, interface) |  | Vertical (pantalla por pantalla) |
| *Preguntas*: ¿cuándo interviene el sistema? ¿qué ve el usuario? |  | *Pregunta*: ¿cómo lo muestra la pantalla? |

**Ejemplo**: tu flujo puede decir "el usuario busca un producto en el catálogo". El wireframe especifica: campo de búsqueda arriba, lista de resultados abajo, filtros a la izquierda, imagen \+ nombre \+ precio por fila.

# **Enfoque centrado en usuario**

Los wireframes exitosos salen de esta pregunta: **¿Qué necesita ver el usuario en esta pantalla para lograr su objetivo?**

No es "qué queremos mostrar", sino "qué le permite actuar". Esto significa:

* **Jerarquía clara**: lo más importante primero, visualmente dominante.  
* **Acciones obvias**: botones y controles donde el usuario los busca (top-right para logout, botón principal en el centro, etc.).  
* **Contexto suficiente**: si el usuario está completando un formulario, incluye indicadores de progreso, ayuda, validación.  
* **Consistencia**: si en pantalla A hay un menú arriba, en pantalla B también.

El wireframe es tu primera prueba de que la estructura **funciona** para el usuario, antes de invertir tiempo en diseño visual.

# **Encargo: Tres wireframes por proyecto**

# **Instrucciones**

Cada estudiante hará **un wireframe para cada una de las 3 interacciones principales** de su producto/app. Las interacciones deben salir del Flow que ya completaron.

# **Formato:**

* Digital, en Figma.  
* Una pantalla por interacción clave (máx. 3 pantallas).  
* Indica elementos con etiquetas simples (botón, campo de entrada, lista, etc.).  
* Incluye una leyenda de 3–5 líneas explicando qué resuelve esta pantalla y por qué está estructurada así.

# **Ejemplo**

**Proyecto**: *PACTO* (Sistema de "pain of paying" en gaming)

**Flujo de usuario (simplificado)**:

1. Usuario abre app → ve saldo disponible (interacción 1: visualizar límite)  
2. Usuario intenta compra → aparece notificación con vibración (interacción 2: fricción/confirmación)  
3. Usuario revisa historial de gastos (interacción 3: reflexión)

**Wireframes a hacer**:

- [ ] WF 1: Dashboard – Saldo & Avisos  
- [ ] WF 2: Confirmación de Compra  
- [ ] WF 3: Reporte Mensual

# **Preguntas guía para cada wireframe**

Antes de empezar, responde esto por cada interacción:

1. **¿Cuál es el objetivo del usuario aquí?** (ej.: "ver cuánto dinero me queda")  
2. **¿Qué información crítica necesita ver?** (ej.: "saldo actual, historial reciente")  
3. **¿Qué acción espero que haga?** (ej.: "decidir si compra o no")  
4. **¿En qué orden lo ve?** (es decir, ¿qué va arriba, qué abajo, qué ocupa más espacio?)  
5. **¿Cómo le hablo si algo no está bien?** (ej.: "aviso si el saldo es bajo")

# **Evaluación**

Usen esta **rúbrica centrada en usuario**:

* ✓ **Claridad**: ¿se entiende qué hace cada elemento sin explicación adicional?  
* ✓ **Jerarquía**: ¿está claro qué es lo más importante en la pantalla?  
* ✓ **Coerencia con flujo**: ¿los wireframes reflejan fielmente las 3 interacciones del Garrett?  
* ✓ **Fundamento**: ¿la leyenda explica *por qué* está estructurado así (no solo qué es)?  
* ✓ **Completitud**: ¿los 3 wireframes forman un viaje coherente del usuario, no son desconectados?

---

**Nota**: Este es el paso entre lo abstracto (flujo) y lo concreto (diseño). No es un formato final; es un prototipo rápido de la estructura. Los errores acá son baratos; los errores en diseño visual son caros.
